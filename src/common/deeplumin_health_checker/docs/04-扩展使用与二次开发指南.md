# 扩展使用与二次开发指南

> 本文档面向"我已经看懂了代码，现在想把它用好/改好"的开发者。内容覆盖：在你的业务节点中集成、各种 CHECK_* API 的实战用法、参数配置技巧、以及常见的二次开发方向。

---

## 第一部分：快速集成 — 5 步在你的节点里启用健康检查

### Step 1：package.xml 添加依赖

```xml
<depend>autoware_health_checker</depend>
```

### Step 2：CMakeLists.txt 链接库

```cmake
find_package(catkin REQUIRED COMPONENTS
  autoware_health_checker
  # ... 你的其他依赖 ...
)

target_link_libraries(your_node ${catkin_LIBRARIES})
```

### Step 3：头文件引入

```cpp
#include <autoware_health_checker/health_checker/health_checker.h>
```

### Step 4：在你的类中创建 HealthChecker 实例

```cpp
class MyPerceptionNode
{
public:
  MyPerceptionNode() : nh_(), pnh_("~")
  {
    // 创建 HealthChecker
    health_checker_ = std::make_shared<autoware_health_checker::HealthChecker>(nh_, pnh);
    
    // ⚠️ 必须调用 ENABLE() 启动后台发布线程！
    health_checker_->ENABLE();
  }
  
private:
  ros::NodeHandle nh_;
  ros::NodeHandle pnh_;
  std::shared_ptr<autoware_health_checker::HealthChecker> health_checker_;
};
```

### Step 5：在业务代码中调用 CHECK_*

```cpp
void MyPerceptionNode::cameraCallback(const sensor_msgs::Image::ConstPtr& msg)
{
  // 1. 频率检查：这个 callback 被调用的频率够不够？
  health_checker_->CHECK_RATE("camera_callback_rate", 25.0, 15.0, 5.0,
    "camera callback rate is too slow");
  
  // 2. 值检查：图像尺寸是否符合预期？
  health_checker_->CHECK_MIN_VALUE("image_height_low", msg->height, 400, 200, 100,
    "image height is too small");
  health_checker_->CHECK_MAX_VALUE("image_height_high", msg->height, 500, 800, 1000,
    "image height is too large");
  
  // 3. 范围检查：FPS 是否在合理区间？
  auto warn_range = std::make_pair(20.0, 40.0);
  auto error_range = std::make_pair(15.0, 50.0);
  auto fatal_range = std::make_pair(10.0, 60.0);
  health_checker_->CHECK_RANGE("fps_out_of_range", current_fps,
    warn_range, error_range, fatal_range, "fps is out of expected range");
  
  // 4. 布尔检查：检测模型是否加载成功？
  health_checker_->CHECK_TRUE("model_loaded", model_is_loaded_,
    deeplumin_msgs::DiagnosticStatus::FATAL,
    "detection model is not loaded");
  
  // 5. 继续正常业务逻辑
  processImage(msg);
}
```

### 完整集成清单

| 步骤 | 做什么 | 容易忘的事 |
|------|--------|-----------|
| 1 | package.xml 加 `<depend>` | 忘加的话编译报找不到头文件 |
| 2 | CMakeLists.txt find_package + target_link_libraries | 没 link 会报 undefined reference |
| 3 | #include 头文件 | 注意用完整路径 |
| 4 | 创建 HealthChecker 实例 + **ENABLE()** | **ENABLE 一定不能忘！** |
| 5 | 调用 CHECK_* 函数 | 记得先在 YAML 里配置参数 |
| 6 | 参数配置 YAML 里注册 key | 没注册的 key 会返回 UNDEFINED |

## 第二部分：所有 CHECK_* API 详解与实战

### 2.1 CHECK_MIN_VALUE — 最小值边界检查

**适用场景**：数值**低于某个阈值**就算异常。

```cpp
health_checker_->CHECK_MIN_VALUE(
  "battery_level_low",           // key（YAML 里的路径）
  battery_percentage,            // 实际值
  20.0,                          // warn 阈值
  10.0,                          // error 阈值
  5.0,                           // fatal 阈值
  "battery level is low"         // 描述
);
```

**判断逻辑**：
```
value < fatal → FATAL
fatal ≤ value < error → ERROR
error ≤ value < warn → WARN
value ≥ warn → OK
```

### 2.2 CHECK_MAX_VALUE — 最大值边界检查

**适用场景**：数值**高于某个阈值**就算异常。

```cpp
health_checker_->CHECK_MAX_VALUE(
  "cpu_usage_high",
  cpu_usage_percent,
  70.0,    // warn
  85.0,    // error
  95.0,    // fatal
  "cpu usage is too high"
);
```

### 2.3 CHECK_RANGE — 范围检查

**适用场景**：数值**超出上下界**都算异常（同时做 MIN 和 MAX 检查）。

```cpp
auto warn_range = std::make_pair(40.0, 60.0);    // warn 范围
auto error_range = std::make_pair(30.0, 70.0);   // error 范围
auto fatal_range = std::make_pair(20.0, 80.0);   // fatal 范围

health_checker_->CHECK_RANGE(
  "temperature_out_of_range",
  current_temperature,
  warn_range, error_range, fatal_range,
  "motor temperature is out of range"
);
```

**判断逻辑**（以 `value < min_threshold || value > max_threshold` 为条件）：
```
value 超出 fatal 范围 → FATAL
value 在 fatal 范围内但超出 error → ERROR
value 在 error 范围内但超出 warn → WARN
value 在 warn 范围内 → OK
```

### 2.4 CHECK_RATE — 频率检查

**适用场景**：某个 callback 或循环被调用的**频率过低**或**完全停止**。

```cpp
// 每次 callback 开头调用
void myCallback(const MyMsg::ConstPtr& msg)
{
  health_checker_->CHECK_RATE(
    "my_topic_rate_slow",        // key
    10.0,                        // warn: 低于 10Hz 警告
    5.0,                         // error: 低于 5Hz 错误
    1.0,                         // fatal: 低于 1Hz 致命
    "my topic rate is too slow"
  );
  
  // ... 正常业务逻辑 ...
}
```

**注意**：
- 这个函数**只是登记调用时间**，不立即产生诊断消息
- 真正的频率计算和发布由后台线程（10Hz）完成
- 冷启动 0.5 秒内不产生任何结果（缓冲窗口长度）

### 2.5 CHECK_TRUE — 布尔/状态检查

**适用场景**：你已经有一个 bool 值，直接指定它对应的级别。

```cpp
// 模型加载失败 → FATAL
health_checker_->CHECK_TRUE("model_not_loaded", 
  !model_loaded_,
  deeplumin_msgs::DiagnosticStatus::FATAL,
  "detection model failed to load");

// 传感器失联 → ERROR
health_checker_->CHECK_TRUE("sensor_disconnected",
  sensor_disconnected,
  deeplumin_msgs::DiagnosticStatus::ERROR,
  "lidar sensor is disconnected");

// 地图过期 → WARN
health_checker_->CHECK_TRUE("map_outdated",
  map_is_old,
  deeplumin_msgs::DiagnosticStatus::WARN,
  "map data is outdated");
```

### 2.6 CHECK_VALUE — 自定义检查逻辑（模板函数）

**适用场景**：以上所有内置 API 都满足不了你复杂的检查逻辑时。

```cpp
// 假设你要检查一个自定义的 PointCloud 结构
struct PointCloudStats {
  int valid_points;
  double avg_distance;
  std::string sensor_name;
};

// 定义检查函数：返回 ErrorLevel
autoware_health_checker::ErrorLevel checkPointCloud(
    const PointCloudStats& stats)
{
  if (stats.valid_points == 0) return AwDiagStatus::FATAL;
  if (stats.avg_distance > 100.0) return AwDiagStatus::ERROR;
  if (stats.sensor_name.empty()) return AwDiagStatus::WARN;
  return AwDiagStatus::OK;
}

// 定义序列化函数：把 stats 转成 JSON ptree
boost::property_tree::ptree statsToJson(const PointCloudStats& stats)
{
  boost::property_tree::ptree pt;
  pt.put("valid_points", stats.valid_points);
  pt.put("avg_distance", stats.avg_distance);
  pt.put("sensor_name", stats.sensor_name);
  return pt;
}

// 调用！
health_checker_->CHECK_VALUE(
  "point_cloud_quality",           // key
  cloud_stats,                     // 值（任意类型）
  checkPointCloud,                 // 检查函数
  statsToJson,                     // 序列化函数
  "point cloud quality is degraded" // 描述
);
```

### 2.7 SET_DIAG_STATUS — 直接设置诊断状态

**适用场景**：你已经有一个完整的 DiagnosticStatus 消息，直接传入。

```cpp
AwDiagStatus status;
status.key = "custom_check_result";
status.level = AwDiagStatus::ERROR;
status.description = "custom check failed";
status.type = AwDiagStatus::INVALID_VALUE;  // 或 OUT_OF_RANGE / UNEXPECTED_RATE
status.header.stamp = ros::Time::now();

health_checker_->SET_DIAG_STATUS(status);
```

### 2.8 NODE_ACTIVATE / NODE_DEACTIVATE — 节点生命周期

```cpp
// 比如车辆启动自动驾驶时
health_checker_->NODE_ACTIVATE();

// 比如安全停车后
health_checker_->NODE_DEACTIVATE();

// HealthAggregator 会把 node_activated=false 的节点
// 从 RViz 的告警列表里过滤掉
```

### 3.5 常见问题：为什么我的 CHECK_* 返回 UNDEFINED？

**原因**：该 key 没有在参数服务器 `health_checker` 命名空间下注册。

**验证**：
```bash
rosparam get health_checker/your_key_name
# 如果返回空或报错，说明没配置
```

**解决**：在 YAML 里加一行，哪怕只写 `your_key_name: default` 也行。

## 第四部分：SystemStatusSubscriber 使用指南

这个库让你可以方便地订阅 `system_status` 并注册多个回调。

### 4.1 基本用法

```cpp
#include <autoware_health_checker/system_status_subscriber/system_status_subscriber.h>

class MyVehicleMonitor
{
public:
  MyVehicleMonitor() : nh_(), pnh_("~")
  {
    status_sub_ = std::make_shared<autoware_health_checker::SystemStatusSubscriber>(nh_, pnh);
    
    // 注册多个回调
    status_sub_->addCallback([](std::shared_ptr<SystemStatus> status) {
      // 回调 1：记录日志
      ROS_INFO_THROTTLE(1.0, "Received system status");
    });
    
    status_sub_->addCallback([this](std::shared_ptr<SystemStatus> status) {
      // 回调 2：检查是否有 FATAL
      for (const auto& node : status->node_status) {
        for (const auto& status_array : node.status) {
          for (const auto& diag : status_array.status) {
            if (diag.level == AwDiagStatus::FATAL) {
              triggerEmergencyStop();
            }
          }
        }
      }
    });
    
    // 必须调用 enable 才会开始订阅
    status_sub_->enable();
  }
  
private:
  std::shared_ptr<autoware_health_checker::SystemStatusSubscriber> status_sub_;
};
```

### 4.2 和 HealthChecker 的关系

`SystemStatusSubscriber` 和 `HealthChecker` 是**两个独立的工具**：
- `HealthChecker` — 用于**发布**健康状态（节点自身上报用）
- `SystemStatusSubscriber` — 用于**订阅**系统状态（其他节点消费全局状态用）

一个节点可以同时使用两者：自己上报状态，同时关注全系统的状态。

## 第五部分：二次开发方向

### 5.1 修改缓冲时间窗口

**文件**：`include/autoware_health_checker/constants.h`

```cpp
constexpr double BUFFER_DURATION = 0.5;  // 改成你想要的值
```

**影响**：
- 值越大 → 过滤抖动效果越好，但反应变慢
- 值越小 → 反应越快，但噪声多

### 5.2 修改发布频率

**文件**：`include/autoware_health_checker/constants.h`

```cpp
constexpr double NODE_STATUS_UPDATE_RATE = 10.0;    // HealthChecker 发布频率
constexpr double SYSTEM_UPDATE_RATE = 30.0;        // HealthAggregator 发布频率
```

### 5.3 扩展诊断级别

当前只用了 4 个级别（OK=1, WARN=2, ERROR=3, FATAL=4，加上 UNDEFINED=0）。如果你想加"INFO"级别，需要：

1. 在 `deeplumin_msgs/DiagnosticStatus.msg` 中添加新常量
2. 在所有遍历 level 的地方（`std::array<ErrorLevel, N>`）加入新级别
3. 修改 HealthAggregator 的 `generateOverlayText` 增加对应颜色
4. 修改 `convertHardwareLevel` 增加映射

### 5.4 在 CHECK_RATE 中增加"连续 N 次失败才报警"的逻辑

当前 `RateChecker` 只看窗口内的频率，不关心"连续多少次"。如果需要"只有连续 3 次回调都慢才报警"：

**修改 `RateChecker`**：
```cpp
class RateChecker {
  // 新增
  int consecutive_failures_ = 0;
  
  boost::optional<LevelRatePair> getErrorLevelAndRate() {
    const auto rate = getRate();
    if (!rate) return boost::none;
    
    // 原来的级别判断
    ErrorLevel level = ...;
    
    // 新增：只有连续失败 N 次才输出非 OK
    if (level != AwDiagStatus::OK) {
      consecutive_failures_++;
      if (consecutive_failures_ < min_consecutive_failures_) {
        level = AwDiagStatus::OK;  // 还没到阈值
      }
    } else {
      consecutive_failures_ = 0;   // 成功则重置
    }
    
    return std::make_pair(level, rate.get());
  }
};
```

### 5.5 HealthAnalyzer 中更智能的根因定位

当前 `findRootNodes` 使用"邻居关系"判断。你可以扩展为：

**方向 A**：考虑边的权重
```cpp
// TopicStatistics 里有 dropped_msgs 和 delivered_msgs
// 丢失率高的 topic 对应的依赖边权重大
// 根节点不仅要看拓扑，还要看数据丢失率
```

**方向 B**：引入"根因传播模型"
```cpp
// 当 A 出问题 → B 收不到数据 → B 也出问题
// 但 B 的问题应该标记为"被 A 影响"，而不是独立告警
// 可以用边的方向传播状态
```

### 5.6 新增一种 CHECK_* 类型

如果你需要检查**消息延迟**而不是频率：

1. 在 `health_checker.h` 声明新函数 `CHECK_LATENCY`
2. 在 `health_checker.cpp` 实现
3. 可能需要新增子模块（类似 `RateChecker`，但存的是时间延迟的统计量）
4. 在 `constants.h` 加默认阈值
5. 在 YAML 模板里加 `latency` 类型

### 5.7 修改 DiagBuffer 的聚合策略

当前策略是"按时间窗口 + 按级别分组 + 取最严重级别"。你可以改成：

**策略 A**：多数投票
```cpp
// 如果窗口内 10 条记录里 8 条 WARN、2 条 OK → 最终 WARN
// 只有 FATAL 数量超过 50% 才输出 FATAL
```

**策略 B**：积分衰减
```cpp
// 每个异常级别有一个分数
// 时间越久远分数权重越低
// 最终分数超过阈值才输出对应级别
```

## 第八部分：常见 FAQ

### Q1：为什么 ENABLE() 必须单独调用？为什么不在构造函数里自动调用？

因为 `std::thread` 的启动时机很微妙。如果在构造函数里启动线程，而构造函数还没执行完（尤其是派生类的构造函数还没开始），线程可能会访问到**尚未完全构造**的成员变量。把线程启动延后到 ENABLE() 是更安全的设计。

### Q2：为什么 CHECK_RATE 不返回 ErrorLevel？它的结果什么时候产生？

CHECK_RATE 只登记调用时间。频率计算在后台线程（publishStatus）里完成。设计原因：
- 后台线程以固定频率批量处理，效率更高
- 避免每个 CHECK_RATE 调用都做完整的窗口清理和计算
- 让 RateChecker 的结果与 DiagBuffer 的结果在**同一个发布周期**内汇总

### Q3：为什么参数查找优先用 YAML 配置，回退到代码默认值？

这是"**配置高于代码**"的设计哲学。默认值保证了即使忘了配置 YAML，系统也能运行（但可能阈值不太合理）。而 YAML 让用户可以按自己的场景调优。

### Q4：为什么 HealthAnalyzer 用 Boost Graph 而不是自己写邻接表？

Boost Graph 是经过工业验证的图算法库，提供了：
- 清晰的图类型定义（adjacency_list、vertex_descriptor、edge_descriptor）
- 遍历接口（vertices、edges、adjacent_vertices）
- 实用算法（write_graphviz 导出 DOT 格式）
- 类型安全的属性挂载（node_property、topic_property）

自己写邻接表虽然也能实现，但容易漏掉边界情况，且复用性差。

### Q5：运行中修改 YAML 阈值后多久生效？

**最快 1 秒，最慢 2 秒**。因为：
1. `ParamManager::getParams` 以 1Hz 刷新参数快照
2. `ValueManager::getValue` 每次调用时取最新的参数快照
3. 如果当前正在 getValue 之前刚拉了参数，新值在下一次 getValue 时生效

### Q6：HealthChecker 的析构安全吗？

安全。析构函数先 `store(true)` 通知后台线程退出，然后 `join()` 等线程真正结束。`joinable()` 检查保证如果 ENABLE() 没被调用（线程没创建），不会对空线程 join。
