# autoware_health_checker 整体框架与设计思路

> 本文档面向希望深入理解 autoware 健康检查系统的开发者，从架构层面梳理整个模块的设计意图、组件关系和数据流。

---

## 1. 这个包到底在做什么？

`autoware_health_checker` 是自动驾驶平台 **Autoware** 的**健康自监测系统**。它的核心使命可以概括为三句话：

1. **让每个节点自己汇报"我好不好"** — 每个功能节点（如感知、规划、控制）通过 `HealthChecker` 库定期上报自己的健康状态。
2. **汇总所有节点的健康信息** — `HealthAggregator` 节点收集所有节点的状态，加上硬件诊断信息，生成统一的系统状态。
3. **定位问题根源** — `HealthAnalyzer` 节点利用节点间的发布/订阅依赖关系图，找出"根节点故障"（即导致其他节点告警的源头节点）。

整个设计遵循 **"分布式上报 + 集中式汇总 + 智能分析"** 的三层架构。

### 2.1 HealthChecker（库）— 节点自监测的核心

**文件位置**：`include/autoware_health_checker/health_checker/` + `src/health_checker/`

**角色**：这是一个 **C++ 库**，不是独立节点。每个业务节点（如 `perception`、`planning`）在代码中 `#include` 它，然后就可以调用一系列 `CHECK_*` 函数来上报自己的健康状态。

**核心职责**：
- 提供 `CHECK_MIN_VALUE` / `CHECK_MAX_VALUE` / `CHECK_RANGE` / `CHECK_RATE` / `CHECK_TRUE` 等 API
- 在内部通过后台线程以 10Hz 频率发布 `node_status` 消息
- 管理阈值参数（从 ROS 参数服务器动态读取）
- 暂存诊断数据（DiagBuffer），防止因偶发异常频繁报警

**包含的子模块**：

| 子模块 | 文件 | 职责 |
|--------|------|------|
| `HealthChecker` | `health_checker.h/.cpp` | 对外暴露的主 API 类，组合下面所有子模块 |
| `DiagBuffer` | `diag_buffer.h/.cpp` | 诊断数据缓冲器，按时间窗口聚合不同级别的状态 |
| `RateChecker` | `rate_checker.h/.cpp` | 频率监测器，计算回调频率并与阈值比较 |
| `ValueManager` | `value_manager.h/.cpp` | **继承自 ParamManager**，管理具体的 warn/error/fatal 阈值数值 |
| `ParamManager` | `param_manager.h/.cpp` | 定期从 ROS 参数服务器读取/写入诊断参数的基础管理器 |

### 2.2 HealthAggregator（独立节点）— 信息汇总中心

**文件位置**：`include/autoware_health_checker/health_aggregator/` + `src/health_aggregator/`

**启动方式**：`roslaunch autoware_health_checker health_checker.launch`

**角色**：这是一个**独立运行的 ROS 节点**，相当于整个健康系统的"中枢"。

**核心职责**：
- 订阅所有节点发布的 `node_status` 话题（类型：`deeplumin_msgs/NodeStatus`）
- 订阅硬件诊断话题 `diagnostics_agg`（标准 ROS 诊断话题）
- 周期性检测节点连接状态（通过 `ros::master::getNodes`）
- 将所有信息整合成统一的 `system_status` 消息（类型：`deeplumin_msgs/SystemStatus`）并发布
- 以 RViz 可视化 OverlayText 的形式，分别在屏幕四个象限显示 OK/WARN/ERROR/FATAL 信息

**包含的子模块**：

| 子模块 | 文件 | 职责 |
|--------|------|------|
| `HealthAggregator` | `health_aggregator.h/.cpp` | 主类，协调所有订阅、发布和定时任务 |
| `StatusMonitor` | `status_monitor.h/.cpp` | 节点超时监测。如果某个节点很久没发布状态，就标记为 ERROR |
| `TimeoutManager` | 内嵌于 `status_monitor.h` | 辅助类，记录单个节点的最后更新时间和超时阈值 |

### 2.3 HealthAnalyzer（独立节点）— 智能根因分析

**文件位置**：`include/autoware_health_checker/health_analyzer/` + `src/health_analyzer/`

**启动方式**：`roslaunch autoware_health_checker health_analyzer.launch`

**角色**：这是一个**独立运行的 ROS 节点**，负责"更聪明地"处理健康数据。

**核心职责**：
- 订阅 `system_status` 话题
- 利用 ROS 的 `topic_statistics` 信息构建**节点依赖关系图**（谁发布给谁，谁是上游，谁是下游）
- 当发现大量告警节点时，在图中定位**根节点**（Root Node）— 即那些没有被其他告警节点依赖的节点，它们才可能是问题的真正源头
- 发布**过滤后的**系统状态（只包含根节点告警），避免"告警风暴"干扰排查

**关键设计**：使用 `boost::graph` 库构建有向图，每条边代表"发布者 → 订阅者"的依赖关系。

### 2.4 SystemStatusSubscriber（库）— 便捷的订阅封装

**文件位置**：`include/autoware_health_checker/system_status_subscriber/` + `src/system_status_subscriber/`

**角色**：一个**轻量库**，供其他节点方便地订阅 `system_status`。

**设计亮点**：支持**多回调注册**——多个模块可以向同一个 `SystemStatusSubscriber` 实例注册各自的回调函数，一条消息来了所有回调都会被触发。这是一个**观察者模式**的实现。

### 话题通信总结

| 话题名 | 类型 | 发布方 | 订阅方 | 频率 | 用途 |
|--------|------|--------|--------|------|------|
| `node_status` | `NodeStatus` | 每个业务节点（HealthChecker 库） | HealthAggregator | 10Hz | 各节点上报自身健康状态 |
| `diagnostics_agg` | `DiagnosticArray` | diagnostic_aggregator （标准 ROS） | HealthAggregator | ~1Hz | 硬件诊断信息 |
| `system_status` | `SystemStatus` | HealthAggregator | HealthAnalyzer、SystemStatusSubscriber、RViz | 30Hz | 汇总后的系统整体状态 |
| `system_status/summary` | `SystemStatus` | HealthAnalyzer | 下游节点 | 跟随上游 | 根节点过滤后的精简状态 |
| `ok_text` / `warn_text` / `error_text` / `fatal_text` | `OverlayText` | HealthAggregator | RViz | 30Hz | 屏幕四角可视化文字 |

## 4. 核心设计模式

### 4.1 参数驱动的阈值管理

所有告警阈值都不硬编码，而是通过 **ROS 参数服务器**（Parameter Server）动态加载。配置 YAML 格式如下：

```yaml
health_checker:
  my_topic_rate_slow:
    rate:
      warn: 8.0     # 低于 8Hz 警告
      error: 5.0    # 低于 5Hz 错误
      fatal: 2.0    # 低于 2Hz 致命
  my_value_out_of_range:
    min:
      warn: 10.0
      error: 5.0
      fatal: 0.0
    max:
      warn: 90.0
      error: 95.0
      fatal: 100.0
```

`ParamManager` 以 1Hz 的定时器定期从参数服务器刷新 `health_checker` 命名空间下的参数。这意味着你可以**运行时动态修改阈值**，无需重启节点。

### 4.2 缓冲抑制（Buffer Suppression）

**问题**：传感器偶尔跳变 → 瞬间 ERROR → 马上恢复 OK → 又跳变 ERROR... 这样会产生大量噪声告警。

**解决方案**：`DiagBuffer` 维护一个 **0.5 秒的滑动时间窗口**（由常量 `BUFFER_DURATION = 0.5` 定义）。只有连续超过 0.5 秒的异常才会被真正发布出去。`getAndClearData()` 在每次被调用时：
1. 先调用 `updateBuffer()` 清理过期数据
2. 按优先级从高到低（FATAL → ERROR → WARN → OK → UNDEFINED）汇总
3. 清空缓冲区
4. 返回汇总结果

这样就把"毛刺"过滤掉了，只保留"持续异常"。

### 4.3 节点依赖图根因定位

**问题**：当感知节点出了一个小问题 → 规划节点收不到数据 → 控制节点也跟着炸 → 看起来全系统都挂了。但真正的根因只有感知节点。

**解决方案**：
1. `HealthAnalyzer` 利用 ROS 的 `rosgraph_msgs/TopicStatistics` 构建**有向依赖图**（Publisher → Subscriber）
2. `findWarningNodes()` / `findErrorNodes()` 找出所有有告警的节点
3. `findRootNodes()` 在依赖图中搜索：如果一个告警节点**没有被其他告警节点依赖**（即它的上游邻居都不是告警节点），它就是根节点
4. 只保留根节点的告警，发布到 `system_status/summary`

这可以大幅降低排查问题时的认知负担。

### 4.4 观察者模式（Observer Pattern）

`SystemStatusSubscriber` 实现了经典的观察者模式：
- 主体（Subject）：`SystemStatusSubscriber`，负责订阅 ROS 话题
- 观察者（Observer）：任意数量的 `std::function` 回调函数
- 通过 `addCallback()` 注册，收到消息时所有回调依次执行

### 4.5 库式集成 vs 节点式运行

整个包采用了**混合架构**：
- `HealthChecker` 是**库** — 需要嵌入到每个业务节点中，天然获得该节点的 ROS 上下文（日志、参数、生命周期）
- `HealthAggregator` 和 `HealthAnalyzer` 是**独立节点** — 作为系统级组件，与具体业务解耦，可以单独启停

这种设计的好处是：业务节点几乎"零成本"就能获得健康监测能力，只需要在代码里调用几个 `CHECK_*` 函数即可。

## 5. 线程模型

```
HealthChecker 内部的线程：

主线程 (业务节点的回调循环)
  ├── 调用 CHECK_* 函数 → 修改 DiagBuffer / RateChecker（加锁保护）
  └── ros::spin() 处理订阅回调

后台发布线程 (在 ENABLE() 中启动)
  └── publishStatus() 以 10Hz 循环：
        ├── 从 RateChecker 读取频率检查结果
        ├── 从 DiagBuffer 读取并清空诊断数据
        └── 发布 node_status 话题

ParamManager 内部的 ROS 定时器回调 (运行在 ros::Timer 线程中)
  ├── getParams() 每 1 秒从参数服务器拉取最新参数
  └── setParams() 每 1 秒把新注册的 key 写入 /diag_reference
```

**互斥锁使用**：
- `HealthChecker::mtx_`：保护 `diag_buffers_` 和 `rate_checkers_` 的访问
- `DiagBuffer::mtx_`：保护缓冲区的读写
- `RateChecker::mtx_`：保护频率数据的读写
- `ParamManager::param_mtx_`：保护参数值的读写
- `ParamManager::key_mtx_`：保护候选 key 集合的读写

## 7. 关键常量

在 `constants.h` 中定义了几个贯穿整个系统的常量：

```cpp
constexpr double BUFFER_DURATION = 0.5;       // DiagBuffer 的时间窗口（秒）
constexpr double NODE_STATUS_UPDATE_RATE = 10.0;  // 各节点状态发布频率（Hz）
constexpr double SYSTEM_UPDATE_RATE = 30.0;    // HealthAggregator 系统状态发布频率（Hz）
```

### 为什么 BUFFER_DURATION 是 0.5 秒？
- 太长：短暂的异常会被掩盖
- 太短：缓冲抑制效果不明显
- 0.5 秒是一个折中值，大约能过滤 10Hz 发布周期中的 5 个瞬时抖动

### 为什么 NODE_STATUS_UPDATE_RATE 是 10Hz？
- 足够快，让聚合器几乎实时地感知到节点状态变化
- 又不会给系统带来太大负担

### 为什么 SYSTEM_UPDATE_RATE 是 30Hz？
- 聚合器要汇总所有节点 + 硬件状态，工作量大，频率略低
- 30Hz 对于"系统整体状态"来说已经足够流畅
- 同时也是 RViz 显示的舒适刷新率

## 8. 消息类型层级

整个系统用到两个关键的 Autoware 自定义消息：

### DiagnosticStatus（单次诊断项）
```
uint8 UNDEFINED=0  —— 未定义
uint8 OK=1         —— 正常
uint8 WARN=2       —— 警告
uint8 ERROR=3      —— 错误
uint8 FATAL=4      —— 致命错误

uint8 INVALID_VALUE=0       —— 值异常
uint8 OUT_OF_RANGE=1        —— 超出范围
uint8 UNEXPECTED_RATE=2     —— 频率异常
uint8 HARDWARE=3            —— 硬件异常

Header header
string key                  —— 唯一标识
uint8 level                 —— 严重级别
uint8 type                  —— 异常类型
string description          —— 人类可读描述
string value                —— JSON 格式的实际值
```

### NodeStatus（节点整体状态）
```
Header header
string node_name
bool node_activated                   —— 节点是否处于激活状态
DiagnosticStatusArray[] status        —— 该节点的所有诊断项
```

### SystemStatus（系统整体状态）
```
Header header
NodeStatus[] node_status              —— 所有业务节点的状态
HardwareStatus[] hardware_status       —— 所有硬件的状态
string[] available_nodes              —— 当前在线的节点名列表
bool detect_too_match_warning         —— 告警数量是否过多（分析器添加）
```

## 9. 启动顺序与依赖

一个典型的启动顺序：

```bash
# 前提：roscore 已经运行
roscore

# 1. 先加载参数（所有 health_checker 相关的阈值）
rosparam load health_checker_params.yaml

# 2. 启动 ROS 标准诊断聚合器（硬件诊断用）
rosrun diagnostic_aggregator diagnostic_aggregator

# 3. 启动健康检查汇总节点
roslaunch autoware_health_checker health_checker.launch

# 4. 启动健康分析节点（可选，用于根因分析）
roslaunch autoware_health_checker health_analyzer.launch

# 5. 启动你的业务节点（它们内部会自动接入 HealthChecker）
roslaunch my_perception perception.launch
roslaunch my_planning planning.launch
# ...
```

## 10. 设计优势总结

| 优势 | 说明 |
|------|------|
| **低侵入性** | 业务节点只需要链接一个库，调用几个 CHECK_* 函数，几乎无负担 |
| **参数驱动** | 所有阈值可通过 YAML 配置、运行时动态调整 |
| **抗抖动** | DiagBuffer 时间窗口过滤瞬时异常，避免告警风暴 |
| **可扩展** | 通过 CHECK_VALUE 模板函数，用户可以注入自定义的检查逻辑 |
| **根因定位** | HealthAnalyzer 利用依赖图自动找出问题源头 |
| **线程安全** | 所有共享数据都用 mutex 保护 |
| **可视化友好** | 支持 RViz OverlayText 实时显示各级别告警 |
| **生命周期感知** | 通过 NODE_ACTIVATE / NODE_DEACTIVATE 感知节点激活/挂起 |
