## 1. ParamManager — 参数管理的基石

**文件**：[param_manager.h](file:///media/nvidia/4T/autoware.ai/src/autoware/common/autoware_health_checker/include/autoware_health_checker/health_checker/param_manager.h) / [param_manager.cpp](file:///media/nvidia/4T/autoware.ai/src/autoware/common/autoware_health_checker/src/health_checker/param_manager.cpp)

**设计定位**：这是整个参数体系的地基。它不负责"具体阈值是多少"，只负责**从 ROS 参数服务器读写原始数据**，以及追踪"有哪些 key 被注册了"。`ValueManager` 和 `HealthAggregator` 都依赖它。

### 1.1 构造函数

```cpp
ParamManager::ParamManager(ros::NodeHandle nh, ros::NodeHandle pnh)
  : nh_(nh), pnh_(pnh)
{
  nh_.getParam("health_checker", params_);
  get_timer_ =
    nh_.createTimer(ros::Duration(1.0), &ParamManager::getParams, this);
  set_timer_ =
    nh_.createTimer(ros::Duration(1.0), &ParamManager::setParams, this);
}
```

**逐行解读**：
- `nh_.getParam("health_checker", params_)` — 节点启动时**立即**从参数服务器拉取一次 `health_checker` 命名空间下的所有参数，存到 `params_`（类型是 `XmlRpc::XmlRpcValue`，可以看作一个动态类型的嵌套字典）。
- `createTimer(ros::Duration(1.0), &ParamManager::getParams, this)` — 创建一个 **1 秒周期的 ROS 定时器**，周期性地调用 `getParams` 成员函数。这实现了"运行时参数热更新"。
- `createTimer(..., &ParamManager::setParams, this)` — 另一个 1 秒定时器，周期性地把新注册的 key 写回参数服务器的 `/diag_reference` 路径下（用于让用户知道有哪些可用的 key）。

### 1.2 addCandidate — 注册新的监测 key

```cpp
void ParamManager::addCandidate(const ErrorKey& key)
{
  std::lock_guard<std::mutex> lock(key_mtx_);
  cached_candidate_key_.emplace(key);
}
```

**逻辑**：
- 每次某个 `CHECK_*` 函数被调用时，它的 key 会被添加到一个 **`std::set<ErrorKey>`** 里（`set` 自动去重，所以同一 key 多次调用不会重复添加）。
- 加锁是因为这个函数可能在主线程被调用，而定时器回调也会访问这个集合。

### 1.3 isNotFound — 查询参数是否存在

```cpp
bool ParamManager::isNotFound(const ErrorKey& key)
{
  std::lock_guard<std::mutex> lock(param_mtx_);
  return !params_.valid() || !params_.hasMember(key);
}
```

**逻辑**：
- `params_.valid()` — 判断 XmlRpcValue 对象是否有效（防止空指针）。
- `params_.hasMember(key)` — 判断该 key 是否在参数服务器中被配置过。
- **双参版本** `isNotFound(ns, key)` — 检查嵌套结构，比如先检查是否有 `ns` 这个命名空间，再检查里面是否有 `key`。HealthAggregator 处理硬件诊断时用这个版本（key 格式是 `"硬件名/字段名"`，拆成 ns 和 key 分开查）。

**这个函数的关键意义**：如果某个 key 没有在参数服务器配置过，那么所有针对它的 `CHECK_*` 调用都会**直接返回 UNDEFINED**，不会产生任何诊断输出。这是一个**安全闸门**——让用户明确配置哪些监测项是"启用"的。

### 1.4 getParams — 定时拉取（定时器回调）

```cpp
void ParamManager::getParams(const ros::TimerEvent& event)
{
  XmlRpc::XmlRpcValue param;
  nh_.getParam("health_checker", param);
  std::lock_guard<std::mutex> lock(param_mtx_);
  params_ = param;
}
```

**逻辑**：
- 先在**锁外**拉取参数（避免阻塞其他线程太久）。
- 拉取完成后**加锁交换**，确保线程安全。

### 1.5 setParams — 定时写入候选 key（定时器回调）

```cpp
void ParamManager::setParams(const ros::TimerEvent& event)
{
  std::set<ErrorKey> keys;
  {
    std::lock_guard<std::mutex> lock(key_mtx_);
    keys = cached_candidate_key_;
    cached_candidate_key_.clear();
  }
  static std::set<ErrorKey> previous_keys;
  for (const auto& key : keys)
  {
    if (previous_keys.count(key) == 0)
    {
      nh_.setParam("diag_reference/" + key, "default");
    }
  }
  previous_keys.insert(keys.begin(), keys.end());
}
```

**逻辑**：
- **Step 1**：把缓存的 key 集合"倒出来"（取副本 + 清空），然后立即释放锁。这样不会在持锁状态下做 ROS API 调用（`setParam`），避免潜在死锁。
- **Step 2**：用 `static` 变量 `previous_keys` 记录**已经写入过**的 key。对每个新 key，调用 `nh_.setParam("diag_reference/" + key, "default")`。
- 这个设计允许用户运行 `rosparam dump dump.yaml /diag_reference` 来查看系统中目前有哪些可用的诊断 key。

## 2. ValueManager — 阈值数值的具体管理器

**文件**：[value_manager.h](file:///media/nvidia/4T/autoware.ai/src/autoware/common/autoware_health_checker/include/autoware_health_checker/health_checker/value_manager.h) / [value_manager.cpp](file:///media/nvidia/4T/autoware.ai/src/autoware/common/autoware_health_checker/src/health_checker/value_manager.cpp)

**设计定位**：**继承自 ParamManager**。如果说 ParamManager 是个"参数字典阅读器"，那 ValueManager 就是"在字典里查找具体数值的专家"。它负责把"key + 阈值类型 + 严重级别"三个维度映射到一个具体的数值上。

### 2.1 setDefaultValue — 设置默认阈值

```cpp
void ValueManager::setDefaultValue(
  const ErrorKey& key, const ThreshType& thresh_type,
  const double warn_value, const double error_value, const double fatal_value)
{
  const auto category = std::make_pair(key, thresh_type);
  error_details_[std::make_pair(category, AwDiagStatus::WARN)] = warn_value;
  error_details_[std::make_pair(category, AwDiagStatus::ERROR)] = error_value;
  error_details_[std::make_pair(category, AwDiagStatus::FATAL)] = fatal_value;
}
```

**逻辑**：
- 这个函数在 `CHECK_MIN_VALUE` / `CHECK_MAX_VALUE` 等被调用时触发。它把**硬编码的默认值**存到 `error_details_` 这个 map 里。
- 为什么需要默认值？因为参数服务器里可能只配置了 `error` 和 `fatal`，没配 `warn`。这时默认值就会被用来填充缺口。
- map 的 key 很巧妙：`std::pair<std::pair<ErrorKey, ThreshType>, ErrorLevel>` 是一个三层复合 key，可以唯一确定一个阈值。

### 2.2 getValue — 获取阈值（优先从参数服务器，回退到默认值）

```cpp
boost::optional<double> ValueManager::getValue(const ErrorKey& key,
  const ThreshType& thresh_type, const ErrorLevel level)
{
  const std::string level_name =
    (level == AwDiagStatus::WARN) ? "warn" :
    (level == AwDiagStatus::ERROR) ? "error" :
    (level == AwDiagStatus::FATAL) ? "fatal" :
    std::string();
  auto diag_params = getParams();
  if (level_name.empty() || !diag_params.hasMember(key))
  {
    return boost::none;
  }
  const bool has_level = diag_params[key].hasMember(thresh_type) ?
    diag_params[key][thresh_type].hasMember(level_name) : false;
  const auto category = std::make_pair(key, thresh_type);
  return (has_level) ?
    static_cast<double>(diag_params[key][thresh_type][level_name]) :
    error_details_.at(std::make_pair(category, level));
}
```

**逻辑**（完整的查找流程）：
1. 先把 `ErrorLevel`（数字 2/3/4）翻译成字符串 `"warn"` / `"error"` / `"fatal"`。
2. 从 ParamManager 获取当前最新的参数快照。
3. 如果 level_name 为空（比如传了 OK 级别）或者 key 根本没在参数里配置 → 返回 `boost::none`（空值）。
4. 检查参数服务器中是否存在 `diag_params[key][thresh_type][level_name]` 这个路径。
5. 如果有 → 用**参数服务器的配置值**（优先级高，可运行时改）。
6. 如果没有 → 回退到 `error_details_` 中的**默认值**。

**这就是参数覆盖机制的完整实现**：YAML 里配了就用 YAML 的，没配就用代码里写的默认值。

## 3. RateChecker — 频率监测器

**文件**：[rate_checker.h](file:///media/nvidia/4T/autoware.ai/src/autoware/common/autoware_health_checker/include/autoware_health_checker/health_checker/rate_checker.h) / [rate_checker.cpp](file:///media/nvidia/4T/autoware.ai/src/autoware/common/autoware_health_checker/src/health_checker/rate_checker.cpp)

**设计定位**：一个纯粹的**滑动窗口频率计算器**。你每次调用 `check()` 就相当于"我收到了一条消息"，它自动帮你算出最近 0.5 秒内收了多少条，再除以 0.5 就是频率。

### 3.1 核心数据结构

```cpp
std::vector<ros::Time> data_;   // 每次 check() 被调用的时间戳
double buffer_duration_;        // 窗口长度（0.5 秒）
double warn_rate_, error_rate_, fatal_rate_;   // 三级阈值
ros::Time start_time_;          // 启动时间，用于"冷启动"时的保护
```

### 3.2 update — 清理过期数据

```cpp
void RateChecker::update()
{
  std::lock_guard<std::mutex> lock(mtx_);
  std::vector<ros::Time> buffer;
  for (const auto& el : data_)
  {
    if (el + ros::Duration(buffer_duration_) > ros::Time::now())
    {
      buffer.emplace_back(el);
    }
  }
  data_ = buffer;
}
```

**逻辑**：
- 遍历所有时间戳，只保留"距离现在不超过 buffer_duration_"的。
- 用 `buffer` 作中间变量，最后整体赋值替换。这比一边遍历一边删除更安全。

### 3.3 check — 登记一次调用

```cpp
void RateChecker::check()
{
  update();
  std::lock_guard<std::mutex> lock(mtx_);
  data_.emplace_back(ros::Time::now());
}
```

**逻辑**：先清理旧数据，再把当前时间戳加进去。每次调用 `CHECK_RATE` 时都会触发这个函数。

### 3.4 getRate — 计算当前频率

```cpp
boost::optional<double> RateChecker::getRate()
{
  boost::optional<double> rate;
  if (ros::Time::now() < start_time_ + ros::Duration(buffer_duration_))
  {
    return boost::none;
  }
  update();
  std::lock_guard<std::mutex> lock(mtx_);
  rate = data_.size() / buffer_duration_;
  return rate;
}
```

**冷启动保护**：
- 系统刚启动时，数据量还不够一个完整窗口。这时如果直接计算，频率会偏低，可能产生误报。
- 解决方法：只有当 `now >= start_time_ + buffer_duration_` 时才开始计算。也就是启动 0.5 秒之后才开始正常工作。

### 3.5 getErrorLevelAndRate — 判断频率状态

```cpp
boost::optional<LevelRatePair> RateChecker::getErrorLevelAndRate()
{
  const auto rate = getRate();
  if (!rate) { return boost::none; }
  const ErrorLevel level =
    (rate.get() < fatal_rate_) ? AwDiagStatus::FATAL :
    (rate.get() < error_rate_) ? AwDiagStatus::ERROR :
    (rate.get() < warn_rate_) ? AwDiagStatus::WARN :
    AwDiagStatus::OK;
  return std::make_pair(level, rate.get());
}
```

**判断逻辑**（注意是 `<`，即频率**越低**越严重）：
- `rate < fatal_rate` → FATAL
- `fatal_rate ≤ rate < error_rate` → ERROR
- `error_rate ≤ rate < warn_rate` → WARN
- `rate ≥ warn_rate` → OK

## 4. DiagBuffer — 诊断数据缓冲器

**文件**：[diag_buffer.h](file:///media/nvidia/4T/autoware.ai/src/autoware/common/autoware_health_checker/include/autoware_health_checker/health_checker/diag_buffer.h) / [diag_buffer.cpp](file:///media/nvidia/4T/autoware.ai/src/autoware/common/autoware_health_checker/src/health_checker/diag_buffer.cpp)

**设计定位**：按 key 存储诊断状态的"时间窗口缓冲区"。核心功能是**聚合 + 去抖**。

### 4.1 核心数据结构

```cpp
std::map<ErrorLevel, DiagnosticStatusArray> buffer_;
```

这是一个按错误级别分层存储的 map。每个级别下是一个 `DiagnosticStatusArray`（即多条 DiagnosticStatus 的集合）。

### 4.2 addDiag — 添加一条诊断记录

```cpp
void DiagBuffer::addDiag(deeplumin_msgs::DiagnosticStatus status)
{
  std::lock_guard<std::mutex> lock(mtx_);
  buffer_[status.level].status.emplace_back(status);
  updateBuffer();
}
```

**逻辑**：
1. 根据 `status.level` 找到对应级别的桶
2. 把新状态追加进去
3. 立即调用 `updateBuffer()` 清理过期数据

### 4.3 updateBuffer — 清理过期数据

```cpp
void DiagBuffer::updateBuffer()
{
  static const std::array<ErrorLevel, 5> level_array =
  { FATAL, ERROR, WARN, OK, UNDEFINED };
  ros::Time now = ros::Time::now();
  for (const auto& level : level_array)
  {
    buffer_[level] = filterBuffer(now, level);
  }
}
```

遍历 5 个级别，对每个级别调用 `filterBuffer`。

### 4.4 filterBuffer — 过滤过期条目

```cpp
DiagnosticStatusArray DiagBuffer::filterBuffer(ros::Time now, ErrorLevel level)
{
  DiagnosticStatusArray filtered_data;
  if (buffer_.count(level) != 0)
  {
    filtered_data = buffer_.at(level);
  }
  DiagnosticStatusArray ret;
  for (const auto& data : filtered_data.status)
  {
    if ((data.header.stamp + buffer_duration_) > now)
    {
      ret.status.emplace_back(data);
    }
  }
  return ret;
}
```

只保留 `data.header.stamp + 0.5s > now` 的条目。即只保留 **0.5 秒以内**的记录。

### 4.5 getAndClearData — 获取并清空（最关键的函数！）

```cpp
DiagnosticStatusArray DiagBuffer::getAndClearData()
{
  static const std::array<ErrorLevel, 4> level_array =
  { ERROR, WARN, OK, UNDEFINED };
  std::lock_guard<std::mutex> lock(mtx_);
  updateBuffer();
  auto data = buffer_.at(AwDiagStatus::FATAL);
  auto& status = data.status;
  for (const auto& level : level_array)
  {
    const auto& buf_status = buffer_.at(level).status;
    status.insert(status.end(), buf_status.begin(), buf_status.end());
  }
  std::sort(status.begin(), status.end(),
    std::bind(&DiagBuffer::isOlderTimestamp, this,
    std::placeholders::_1, std::placeholders::_2));
  buffer_.clear();
  return data;
}
```

**逐步解读**：

这是 HealthChecker 后台发布线程每次发布时调用的函数，逻辑极其精妙：

1. **加锁 + 清理过期数据**
2. **以 FATAL 级别作为起点**（它有最高优先级）。先拿出 FATAL 桶里的所有记录。
3. **按顺序拼接**：ERROR → WARN → OK → UNDEFINED，依次追加到后面。
4. **按时间戳排序**：使用 `std::sort` + `std::bind` 绑定成员函数，把所有记录按时间先后排列。
5. **清空整个 buffer**：发布完了就清空，下一个周期从零开始积累。
6. **返回合并后的结果**。

**设计含义**：
- 如果在缓冲窗口内既有 FATAL 又有 OK → 返回结果里**同时包含两者**，但 FATAL 排在前面。这让聚合器可以看到"严重程度变化的完整过程"。
- 如果窗口内全是 OK → 就只返回 OK。
- **清空操作**确保每个发布周期只报告上一个周期内新产生的状态。

### 4.6 getErrorLevel — 获取最高严重级别

```cpp
ErrorLevel DiagBuffer::getErrorLevel()
{
  static const std::array<ErrorLevel, 4> level_array =
  { FATAL, ERROR, WARN, OK };
  std::lock_guard<std::mutex> lock(mtx_);
  updateBuffer();
  for (const auto& level : level_array)
  {
    if (!buffer_.at(level).status.empty())
    {
      return level;
    }
  }
  return AwDiagStatus::OK;
}
```

从 FATAL 开始逐级查，找到第一个非空的就返回。如果全空就返回 OK。注意这个函数**不会清空 buffer**（和 `getAndClearData` 不同）。

## 5. HealthChecker — 对外 API 的门面

**文件**：[health_checker.h](file:///media/nvidia/4T/autoware.ai/src/autoware/common/autoware_health_checker/include/autoware_health_checker/health_checker/health_checker.h) / [health_checker.cpp](file:///media/nvidia/4T/autoware.ai/src/autoware/common/autoware_health_checker/src/health_checker/health_checker.cpp)

**设计定位**：把前面所有子模块"组装在一起"，对外提供简洁易用的 `CHECK_*` API。

### 5.1 构造和析构

```cpp
HealthChecker::HealthChecker(ros::NodeHandle nh, ros::NodeHandle pnh)
  : value_manager_(nh, pnh)    // ParamManager 的派生类构造
  , node_activated_(false)    // 节点默认未激活
  , nh_(nh)
  , pnh_(pnh)
  , is_shutdown_(false)       // 原子变量，用于线程间通信
{
  status_pub_ =
    nh_.advertise<deeplumin_msgs::NodeStatus>("node_status", 10);
}

HealthChecker::~HealthChecker()
{
  is_shutdown_.store(true);          // 通知后台线程退出
  if (node_status_publish_thread_.joinable())
  {
    node_status_publish_thread_.join();  // 等待线程结束
  }
}
```

**析构函数的优雅退出**：
- `is_shutdown_` 是 `std::atomic<bool>`，可以安全地跨线程读写。
- 先 `store(true)` 通知发布循环里的 `while(!is_shutdown_.load())` 退出。
- 再 `join()` 等待线程结束。如果线程还没启动（`ENABLE` 没被调用），`joinable()` 返回 false，跳过 join。

### 5.2 ENABLE — 启动后台发布线程

```cpp
void HealthChecker::ENABLE()
{
  node_status_publish_thread_ = std::thread(&HealthChecker::publishStatus, this);
}
```

在业务节点中**必须调用**，否则 node_status 永远不会被发布。`this` 作为参数传给线程函数，因为 `publishStatus` 是成员函数。

### 5.3 publishStatus — 后台发布循环

```cpp
void HealthChecker::publishStatus()
{
  const int loop_usec =
    std::round(1.0 / autoware_health_checker::NODE_STATUS_UPDATE_RATE * 1e6);
  const std::string node_name = ros::this_node::getName();

  auto prev_time = std::chrono::system_clock::now();
  ros::Time prev_ros_time = ros::Time::now();
  while (ros::ok() && !is_shutdown_.load())
  {
    const auto until_time = prev_time + std::chrono::microseconds(loop_usec);
    std::this_thread::sleep_until(until_time);
    prev_time = until_time;
    // ...
```

**这段代码的精髓——高精度定时 + 仿真时间兼容**：

1. `loop_usec` — 把 10Hz 转换成微秒：`1/10 * 1e6 = 100000` 微秒 = 100ms。
2. **使用 `std::chrono::system_clock` + `sleep_until`** 而不是简单的 `sleep_for`。这样即使某次循环处理超时了，下次循环也会对齐到"期望时间点"，不会漂移。
3. **仿真时间兼容处理**：
   ```cpp
   const ros::Time now = ros::Time::now();
   if (prev_ros_time == now) { continue; }  // 时间没前进就跳过
   prev_ros_time = now;
   ```
   在 Gazebo 仿真中，如果仿真时间被暂停了，`ros::Time::now()` 就会卡住。这段代码检测到时间没前进就跳过本次发布，避免用过期数据发布。

循环体内部做的事：

```cpp

    status.node_name = node_name;
    status.node_activated = node_activated_;
    status.header.stamp = now;

    std::lock_guard<std::mutex> lock(mtx_);  // 保护共享数据

    // 2. 发布所有 RateChecker 的结果
    for (const auto& key : checker_keys) {
      auto result = rate_checkers_[key]->getErrorLevelAndRate();
      if (result) {
        // 构造一条 DiagnosticStatus，type = UNEXPECTED_RATE
        // 塞进 status.status
      }
    }

    // 3. 发布所有 DiagBuffer 的累积结果
    for (const auto& key : keys) {
      status.status.emplace_back(diag_buffers_.at(key)->getAndClearData());
    }

    // 4. 真正发布
    status_pub_.publish(status);
```

### 5.4 CHECK_MIN_VALUE — 最小值检查（逐行解析）

```cpp
ErrorLevel HealthChecker::CHECK_MIN_VALUE(const ErrorKey& key,
  const double value, const double warn_value, const double error_value,
  const double fatal_value, const std::string& description)
{
  // 第 1 步：注册这个 key
  value_manager_.addCandidate(key);

  // 第 2 步：如果参数服务器没配置这个 key → 静默返回 UNDEFINED
  if (value_manager_.isNotFound(key))
  {
    return AwDiagStatus::UNDEFINED;
  }

  // 第 3 步：保存默认阈值（参数服务器没配时用）
  static const ThreshType thresh_type = "min";
  value_manager_.setDefaultValue(
    key, thresh_type, warn_value, error_value, fatal_value);

  // 第 4 步：定义检查逻辑（value < 阈值？）
  auto identify = [key, value, thresh_type, this](ErrorLevel level)
  {
    return (value < value_manager_.getValue(key, thresh_type, level).get());
  };

  // 第 5 步：创建基础的 DiagnosticStatus 消息
  AwDiagStatus new_status = setValueCommon(key, value, description);

  // 第 6 步：从严重到轻微依次检查，找到第一个触发的级别
  new_status.level = identify(AwDiagStatus::FATAL) ? AwDiagStatus::FATAL :
    identify(AwDiagStatus::ERROR) ? AwDiagStatus::ERROR :
    identify(AwDiagStatus::WARN) ? AwDiagStatus::WARN :
    AwDiagStatus::OK;
  new_status.type = AwDiagStatus::OUT_OF_RANGE;

  // 第 7 步：调用统一入口存入 DiagBuffer
  return SET_DIAG_STATUS(new_status);
}
```

**判断逻辑**（最小值检查，即 value **低于**某阈值就算异常）：
- `value < fatal_threshold` → FATAL
- `fatal ≤ value < error` → ERROR
- `error ≤ value < warn` → WARN  
- `value ≥ warn` → OK

**举个例子**：
```
fatal = 0, error = 5, warn = 10
如果 value = 3 → 3 < 0? No → 3 < 5? Yes → ERROR
如果 value = 8 → 8 < 0? No → 8 < 5? No → 8 < 10? Yes → WARN
```

### 5.6 CHECK_RANGE — 范围检查

把 MIN 和 MAX 合二为一。同时检查"value 是否低于 min 阈值"和"value 是否高于 max 阈值"：

```cpp

{
```

### 5.7 CHECK_RATE — 频率检查

和值检查不同，频率检查**不是每次都产生诊断消息**。它的逻辑是：

```cpp
void HealthChecker::CHECK_RATE(const ErrorKey& key, ...)
{
  value_manager_.addCandidate(key);
  if (value_manager_.isNotFound(key)) return;

  std::lock_guard<std::mutex> lock(mtx_);
  if (!keyExist(key))
  {
    // 第一次调用时创建 RateChecker 实例
    rate_checkers_[key] = std::make_unique<RateChecker>(...);
  }
  // 更新阈值（可能从参数服务器读了新值）
  rate_checkers_[key]->setRate(...);
  // 登记一次调用
  rate_checkers_[key]->check();
  // 创建 buffer（但频率检查结果不是在这里发布的，而是在 publishStatus 里）
  addNewBuffer(key, AwDiagStatus::UNEXPECTED_RATE, description);
}
```

**关键区别**：`CHECK_RATE` 只负责"登记"，真正的频率计算和发布在后台线程的 `publishStatus` 里通过 `rate_checkers_[key]->getErrorLevelAndRate()` 完成。

### 5.8 CHECK_TRUE — 布尔值检查

最简单的检查函数，直接传入一个 level：

```cpp
ErrorLevel HealthChecker::CHECK_TRUE(const ErrorKey& key, const bool value,
  const ErrorLevel level, const std::string& description)
{
  // ...
  AwDiagStatus status = setValueCommon(key, value, description);
  status.level = level;    // 直接使用调用方指定的 level
  status.type = status.INVALID_VALUE;
```

**用法**：比如"传感器连接是否断开"这个布尔判断——如果断开就传 `FATAL`，没断开就传 `OK`。

### 5.9 CHECK_VALUE — 可注入的自定义检查（模板函数）

```cpp
template <class T> ErrorLevel CHECK_VALUE(
  const ErrorKey& key, const T& value,
  std::function<ErrorLevel(T value)> check_func,
  std::function<boost::property_tree::ptree(T value)> value_json_func,
  const std::string& description)
```

**参数解读**：
- `T` — 值的类型，可以是任意类型（double、string、自定义 struct...）
- `check_func` — 调用方提供的**检查函数**，输入值，输出级别。你可以写任意复杂的判断逻辑。
- `value_json_func` — 调用方提供的**序列化函数**，把值转成 JSON ptree。

**意义**：当你需要的检查逻辑不能用简单的 `<` `>` `range` 表达时，用这个模板函数注入自定义逻辑。测试文件里有使用示例：

```cpp
ErrorLevel my_check(double value) {
  if (value == 0.0) return FATAL;
  if (value == 1.0) return ERROR;
  if (value == 2.0) return WARN;
  return OK;
}
CHECK_VALUE("test", value, my_check, my_json_func, "test description");
```

### 5.10 SET_DIAG_STATUS — 统一入口

所有 CHECK_* 函数最终都会走到这里：

```cpp
ErrorLevel HealthChecker::SET_DIAG_STATUS(
  const deeplumin_msgs::DiagnosticStatus& status)
{
  value_manager_.addCandidate(status.key);
  if (value_manager_.isNotFound(status.key)) return AwDiagStatus::UNDEFINED;

  auto identify = [&status](const ErrorLevel target_level)
  {
    return (status.level == target_level);
  };
  // 验证 level 必须是合法值
  if (!identify(AwDiagStatus::OK) && !identify(AwDiagStatus::WARN) &&
    !identify(AwDiagStatus::ERROR) && !identify(AwDiagStatus::FATAL))
  {
    return AwDiagStatus::UNDEFINED;
  }

  std::lock_guard<std::mutex> lock(mtx_);
  addNewBuffer(status.key, status.type, status.description);
  diag_buffers_.at(status.key)->addDiag(status);
  return status.level;
}
```

做两件事：
1. 验证 level 合法性（必须是 OK/WARN/ERROR/FATAL 之一）
2. 确保 buffer 存在（不存在就创建），然后往里面 addDiag

### 6.1 TimeoutManager — 单个节点的计时器

```cpp
class TimeoutManager {
public:
  TimeoutManager() = default;
  explicit TimeoutManager(const double time_out)
    : timer_start_time_(ros::Time::now()), time_out_(time_out) {}
  
  double getDuration(const ros::Time& current) const
  {
    return (current - timer_start_time_).toSec();
  }
  bool isOverLimit(const ros::Time& current) const
  {
    return (getDuration(current) > time_out_);
  }
private:
  ros::Time timer_start_time_;   // 上次更新时间
  double time_out_;              // 超时阈值（秒）
};
```

**逻辑**：每次节点发布状态时 `updateStamp` 重置 `timer_start_time_`。如果 `当前时间 - 上次更新时间 > time_out_`，说明节点卡住了。

### 6.2 StatusMonitor — 管理所有节点的超时

```cpp
class StatusMonitor {
  void updateStamp(const std::string& name, const double timeout)
  {
    std::lock_guard<std::mutex> lock(mtx_);
    timeout_manager_array_[name] = TimeoutManager(timeout);
  }
  
  NodeStatus getMonitorStatus() const
  {
    // 遍历所有 TimeoutManager
    // 如果 isOverLimit → 生成一条 ERROR 级别的 DiagnosticStatus
    // 最后组装成一个 NodeStatus 返回
  }
};
```

**一个细节**：`updateStamp` 每次都会**用新的 TimeoutManager 对象整体替换** map 里的旧值，而不是调用 reset。因为 TimeoutManager 的构造函数会自动获取当前时间戳。这样更简洁。

```cpp
  { return s.node_name == node_status.node_name; };
```

### 8.2 addDepend — 添加一条发布→订阅依赖

```cpp
void addDepend(const rosgraph_msgs::TopicStatistics& statistics)
{
  if (statistics.node_pub == statistics.node_sub) return;  // 自循环跳过
  
  vertex_t node_sub, node_pub;
  
  // 查找或创建顶点
  auto pub_vertex = getTargetNode(statistics.node_pub);
  if (!pub_vertex) {
    pub_vertex = boost::add_vertex(depend_graph_);
    depend_graph_[pub_vertex.get()].node_name = statistics.node_pub;
  }
  // sub_vertex 同理...
  
  // 添加有向边：sub → pub（"sub 依赖 pub"）
  bool inserted = false;
  boost::tie(topic, inserted) =
    boost::add_edge(sub_vertex.get(), pub_vertex.get(), depend_graph_);
}
```

### 8.3 findRootNodes — 找出根节点

```cpp
std::vector<std::string> findRootNodes(const std::vector<std::string>& target_nodes)
{
  std::vector<std::string> ret;
  for (const auto& node : target_nodes)
  {
    bool depend_found = false;
    auto vertex = getTargetNode(node);
    if (!vertex) continue;
    
    // 遍历该节点的所有相邻顶点
    adjacency_iterator_t vi, vi_end;
    boost::tie(vi, vi_end) = adjacent_vertices(vertex.get(), depend_graph_);
    for (; vi != vi_end; ++vi)
    {
      if (isAlreadyExist(target_nodes, depend_graph_[*vi].node_name))
      {
        depend_found = true;  // 找到了一个也在 target_nodes 里的邻居
      }
    }
    
    if (!depend_found)
      ret.emplace_back(node);  // 没有被其他告警节点依赖 → 根节点
  }
  return ret;
}
```

**算法图解**：假设依赖图是 `A → B → C`（A 发布给 B，B 发布给 C）。如果 B 和 C 都出问题了，但 A 正常：
- B 的邻居是 A 和 C。A 不在 target_nodes 里，C 在。→ B 不是根节点（被 C 依赖？不对...）

实际上 `adjacent_vertices` 对 `bidirectionalS` 图返回的是**所有**相邻顶点（不管方向）。所以检查的是"我是否和其他告警节点有连接"。更准确地说，根节点是**在依赖图中没有入边来自其他告警节点**的节点。

## 9. SystemStatusSubscriber — 观察者模式的实现

**文件**：[system_status_subscriber.h](file:///media/nvidia/4T/autoware.ai/src/autoware/common/autoware_health_checker/include/autoware_health_checker/system_status_subscriber/system_status_subscriber.h) / [system_status_subscriber.cpp](file:///media/nvidia/4T/autoware.ai/src/autoware/common/autoware_health_checker/src/system_status_subscriber/system_status_subscriber.cpp)

整个类非常简洁，但设计得很精巧：

```cpp
class SystemStatusSubscriber {
public:
  void enable() {
    status_sub_ = nh_.subscribe("system_status", 10,
      &SystemStatusSubscriber::systemStatusCallback, this);
  }
  
  void addCallback(std::function<void(shared_ptr<SystemStatus>)> func) {
    functions_.emplace_back(func);
  }
  
private:
  void systemStatusCallback(const SystemStatus::ConstPtr msg) {
    for (auto& func : functions_) {
      auto pmsg = std::make_shared<SystemStatus>(*msg);  // 复制一份
      func(pmsg);
    }
  }
  
  std::vector<std::function<void(shared_ptr<SystemStatus>)>> functions_;
};
```

**为什么要复制一份消息？** 因为原始消息 `msg` 是 ROS 内部管理的，回调执行完可能就被释放了。每个回调拿到自己的 `shared_ptr`，可以安全地在异步环境中使用。
