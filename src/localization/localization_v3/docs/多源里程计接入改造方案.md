# 多源里程计接入改造方案（源注册表）

> 版本：v1.0（设计稿，暂不改代码）
> 日期：2026-10-12
> 关联：`dr_odometry_fallback_design.md`（DR 接入方案）、`localization_v3_optimization_plan.md`（v3 主优化）
> 目标：接入新里程计从"改 4 处代码"变为"配置 + 3 行回调"；顺带消除本次踩过的外参配置分叉坑。

---

## 1. 现状评估

### 1.1 已经做对的（保持）

| 项 | 现状 |
|---|---|
| 分层 | core（纯 C++ 零 ROS、可单测）/ ros（薄适配）/ node（仅编排），无逆向依赖 |
| 契约 | 坐标系契约显式（"桥输出的里程计与源点云同处虚拟局部系"）、连续性不变式有测试锁定 |
| 隔离 | fusion_core / state_machine / GM 对源接入**零改动**；回退仅 launch 一处 |
| 配置 | 按功能分组、注释齐全 |

### 1.2 唯一的"补丁味"：源抽象二元硬编码

```cpp
enum class Source { kNone, kSlam, kDr };        // 写死两个源
Pose3d last_slam_, last_dr_, glue_slam_, glue_dr_;
// unifiedPose() 内 switch + 成对转移（kSlam→kDr / kDr→kSlam 各写一遍）
```

切换数学本身是**通用的**（`glue_new = glue_old ⊕ T_old_last ⊕ T_new_last⁻¹`），只有数据结构与仲裁枚举是二元的。现状接入第三个源要改：enum、成员、仲裁分支（N×N 成对）、bridge 订阅、yaml——共 4 处，且易漏。

### 1.3 附带发现的结构坑：**外参配置分叉**（2026-10-12 实测踩坑）

LIO 注册点云用的是**算法内部** `extrinsic_R`（`slam_odometry_v2.yaml` 中 =Rz(-90°)，lidar→IMU 90° 安装），而节点层另有 `extrinsics/base_to_lidar`（=I，仅用于输出变换）。桥的 fallback 注册照抄了节点层的 identity → **注册云相对正确位置差 90°**（DR-only 时暴露，SLAM 模式因透传 LIO 云而正确）。教训：**注册类外参必须单一来源、语义明确**。

---

## 2. 改造目标

1. 接入新里程计 = **配置 1 条 + 订阅回调 3 行**，零改动核心仲裁；
2. 源数量 N 任意，仲裁规则与 N 无关；
3. 坐标系契约、连续性不变式、测试语义全部保留；
4. 外参配置单一来源，注册方共享。

---

## 3. 源注册表设计

### 3.1 数据结构（core/local_odom_source 扩展）

```cpp
using SourceId = int;

struct OdomSourceSpec {
  std::string name;              // "slam" / "dr" / "vio" ...
  int priority = 0;              // 高者优先（slam=10, dr=5, 其他按需）
  double timeout_sec = 0.5;      // 新鲜度判定
  int switch_back_confirm = 5;   // 回到低优先级源的滞回帧数（从高优先级源切回）
  CloudMode cloud_mode;          // kRegistered：源自带注册云（⊕glue 后发布）
                                 // kRawRegister：无注册云（原始点云 ⊕ 统一位姿注册）
};

struct SourceSlot {
  OdomSourceSpec spec;
  Pose3d last_pose;              // 最近样本（源系）
  double last_stamp = -1.0;
  Pose3d glue;                   // 源系→虚拟系粘合（切换时计算）
  int confirm_count = 0;
};
```

### 3.2 仲裁规则（与源数量无关）

```
unifiedPose(now):
  候选 = 所有 fresh(stamp) 的源
  目标 = 候选中 priority 最高者（同级取最新样本）
  无候选 → false（下游看门狗判失效）

  if 目标 != active:
     若目标.priority > active.priority      → 立即切换（主源恢复/更好源出现）
     否则（降级切换）                      → 需 confirm_count ≥ switch_back_confirm（滞回）
     切换时：glue_目标 = (glue_active ⊕ T_active_last) ⊕ T_目标_last⁻¹   ← 通用连续性公式
     记录切换（翻转保护：窗口内切换 ≥ flap_guard_count → confirm 帧数加倍）

  输出 = glue_active ⊕ T_active_last
```

要点：
- **连续性公式与源无关**——现有 `local_odom_source.cpp` 的接管/回切数学原样复用，仅改成表驱动；
- 主备语义通过 `priority` 表达（SLAM 高、DR 低），不再写死"谁主谁备"；
- 新源接入无需动这棵树；
- **gap 填充**（已实现，限检测窗）：kSlam 输出 = `glue_slam ⊕ T_slam_last ⊕ (D_at_slam⁻¹ ⊕ T_dr_now)`，
  仅当样本年龄 > `gap_fill_delay_sec(0.15s)` 且 DR 存活时启用；新鲜期输出**纯 SLAM**——
  DR 不进输出链，切断"DR→输出→定位观测"自回灌（实测该环会造成大幅抖动）；
  接管锚定在 t_s（最后 SLAM 样本时刻）使切换瞬间输出恒等且 gap 运动不丢。
  DR 侧观测门控 `slam_age_limit(0.15s)` 与之对齐：观测期=纯 SLAM 期，零重叠。
  **阈值红线**：必须 > SLAM 里程计周期并留余量（10Hz→0.1s，故 0.15；取 0.12 时实测抖动反复触发 → 毛刺），
  详见 `gap_fill_switch_optimization.md`。

### 3.3 源点云契约（不变，通用化）

> **桥输出的里程计与源点云必须同处虚拟系。** 与 `map_odom`（=map→云端系）组合的一切必须同系。

| cloud_mode | 处理 |
|---|---|
| `kRegistered` | 源的注册云 ⊕ `glue` 变换到虚拟系发布（glue=I 时零成本透传） |
| `kRawRegister` | 原始点云 ⊕ (统一源位姿 ⊕ **T_base_lidar**) 注册发布 |

**T_base_lidar 配置红线**（1.3 教训）：必须与该传感器的真实安装一致，且与 LIO 内部注册外参（如 `extrinsic_R`）同源/等价。建议：

- `source_bridge.yaml` 的 `cloud/base_to_lidar` 注释注明"必须与 slam_odometry_v2 的 extrinsic_R（lidar→IMU）一致"；
- 条件允许时由 launch 统一注入同一组外参（单一来源）；
- 增加一条自检日志：桥启动时打印 base_to_lidar，与 LIO 侧值并排可见。

## 4. 接入新里程计的步骤清单（改造后）

以接入 `vio_odometry`（假设自带注册云）为例：

**① source_bridge.yaml 加一条源 + 外参（如有）**

```yaml
sources:
  slam:   {priority: 10, timeout_sec: 0.5, switch_back_confirm: 5, cloud_mode: registered}
  dr:     {priority: 5,  timeout_sec: 0.5, switch_back_confirm: 5, cloud_mode: raw_register}
  vio:    {priority: 7,  timeout_sec: 0.3, switch_back_confirm: 5, cloud_mode: registered}

topics:
  vio_odom: /localization/vio_odom
  vio_cloud: /localization/vio_cloud      # cloud_mode=registered 时需要
```

**② bridge 节点加一个订阅回调（3 行）**

```cpp
vio_sub_ = nh_.subscribe(topics_.vio_odom, 100,
    [this](const nav_msgs::Odometry::ConstPtr& m) {
      source_.onSample(id_vio_, poseFromRos(m->pose.pose), stampOrNow(m->header.stamp));
    });
// cloud_mode=registered 时同理转发其注册云（⊕glue 路径已有，复用）
```

**③ launch 启动该里程计节点**（`<include>` 一行）

**不需要动**：LocalOdomSource 仲裁、fusion_core、state_machine、GM、失效判定、其他 launch 接线。

### 4.1 各类源的接入差异

| 源类型 | 例子 | cloud_mode | 备注 |
|---|---|---|---|
| 全功能 LIO | slam_odometry_v2 / lio_odometry | registered | 注册云 + odom 都有 |
| 航位推算 | dr_odometry_v2 | raw_register | 只有 odom，云用原始点云注册 |
| 轮速/VIO | dr 的轮速单测速、VIO | raw_register 或 registered | 视其是否发布注册云 |
| 外部组合导航 | 供应商里程计 | registered | 注意其外参约定 |

## 5. 测试与回归

| 层 | 用例 |
|---|---|
| 单测（core） | 多源仲裁：优先级抢占、降级滞回、翻转保护、连续性（任意源对切换 unified 不变）、双源皆失无输出 |
| 单测（云契约） | registered 源 glue 变换后与 unified 同系；raw_register 注册姿与 unified 同刻；glue=I 透传逐字节 |
| 回归 | 现有 8 个 local_odom_source 用例迁移为参数化（语义不变）；104 个 v3 测试全绿 |
| bag | SLAM-only / DR-only / 双源切换 各跑一段，校验 curr_scan_in_map 与 path/TF 重合（本次 90° 问题的验收用例） |

**特别验收**（吸取 1.3 教训）：DR-only 模式下 curr_scan_in_map 的车头方向必须与 TF base_link 的 x 轴一致——这是外参正确性的直接判据。
